# 包的接口与可见性

## R · 原书依据

§11.1–11.4、附录 A.5。按客户需要的可见接口划分包，模拟引入新子类型时的依赖变化。

## I · 如何选择

按客户需要的可见接口划分包，模拟引入新子类型时的依赖变化。
- 区分接口访问层次；有双向依赖时对照合并、互见及取消单向可见三案；将特有子类型置于可见父类型的包中。

## A1 · 原书建模示例

联系人应用和交易应用对主体包的需求不同（§11.2，第 231–233 页，图 11.7–11.8）。联系人应用只需主体资料；交易应用既要查合同双方，也想从主体查已有交易。单向可见会增加反向查询成本，合包会扩大可见面，双向可见引入环；评审时用这两个客户逐案判定取舍。

## A2 · 何时调用

模块 / 可见性 / 插件的建模或评审。语言线索包括 模块 可见性 插件 子包 package。相关但输出不同的任务见「类型模型的实现契约」。

## E · 执行与验收

输入需要客户端调用清单、包与类型依赖。

1. 区分接口访问层次。
2. 有双向依赖时对照合并、互见及取消单向可见三案。
3. 将特有子类型置于可见父类型的包中。

按项目涉及的分支检查：

- 画可见性边的方向并模拟新增子类；确有反向导航的业务需求时重新权衡成本。

输出应包含客户到接口的可见性矩阵。
列出每个客户端可见的名字。让新子类型依赖基础类型，在应用组装处装载扩展，尝试单独构建基础包。

## B · 反例与判停

- 基础包依赖具体期权子类。父类型内嵌可用子类型的假设，未来增加专门类型就必须修改基础包。（§11.3，书页 234）
- 循环关系能否取消要以客户操作核查。
